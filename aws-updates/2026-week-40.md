### Amazon GuardDuty
*Category: Detection & Response | Exam domain: 1 - Threat Detection & Incident Response | Releases: 5*

#### `P1` 2026-10-01 — Amazon GuardDuty now supports centralized management using AWS Organizations declarative policies
- **What changed:** GuardDuty enablement is now expressible as an AWS Organizations declarative policy, attachable at the org root, an OU, or an individual account. The policy carries a default configuration that applies in every Region where GuardDuty is available, plus per-Region overrides. The decisive detail: enablement set by a declarative policy **cannot be overridden through the GuardDuty console or API**. Previously enablement was configured per Region from the delegated administrator and could drift.
- **Why it matters:** This converts GuardDuty enablement from a detective control that has to be continuously reconciled into a preventive one. For a 1,000-tenant platform, the failure mode it removes is a Workload-account operator disabling GuardDuty in a Region that was never on anyone's dashboard. It also eliminates the per-Region enablement script from the foundation deployment.
- **Exam angle:** Domain 1 and Domain 6. Declarative policies are a distinct policy type from SCPs and RCPs, and the testable distinction is *mechanism*: an SCP denies the `guardduty:DisableOrganizationAdminAccount`-style API call, whereas a declarative policy sets and holds the configuration itself so the local API cannot change it. Expect "which policy type guarantees the setting stays enabled" framing.
- **Platform angle:** Attach at the Management Account root. The Audit Account remains the delegated administrator for findings; the declarative policy governs enablement only.
- **Action:** Rewrite the GuardDuty enablement section of `saas-security/organizations/guide.md` and add the declarative-policy type to `exam-study/organizations.md`.
- **Source:** [Amazon GuardDuty now supports centralized management using AWS Organizations declarative policies](https://aws.amazon.com/about-aws/whats-new/2026/10/guardduty-org-enablement-policies/)
- **Docs:** [Managing accounts using organization policies](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty-organization-policies.html)

### AWS Network Security Manager
*Category: Network & Application Protection | Exam domain: 3 - Infrastructure Security | Releases: 1*

#### `P1` 2026-09-24 — AWS Network Security Manager is now generally available in US East (N. Virginia) Region
- **What changed:** A new AWS service reached GA. It introduces a four-level object model — **rules** → **templates** → **policies** → **deployments** — plus **scopes** that select target accounts and resources. Policies are hierarchical: a change to a rule cascades (or rolls back) through every template, policy, and deployment that includes it. Scopes group resources by Organization, account, resource type, or tag. It covers AWS WAF and AWS Shield Advanced today, with AWS Network Firewall announced as coming. Protection targets are internet-facing resources: Application Load Balancers, API Gateway, and CloudFront distributions. Per-policy switches control **Remediation** (re-apply when a resource drifts from the declared state), **Resource cleanup** (delete the protection when the resource leaves scope), and conflict resolution against pre-existing customer protections. It also reports per-policy synchronization state so drift is visible.
- **Why it matters:** This is the first AWS-native service that treats a WAF rule set as a versioned, hierarchical artifact deployed org-wide with drift detection, rather than a per-web-ACL configuration. The "central baseline plus application-team additions merged into one configuration per resource" model maps directly onto a 1,000-tenant platform where a central security team owns the non-negotiable rules and tenant-facing teams add their own. It also overlaps substantially with AWS Firewall Manager, and that overlap has to be resolved before either the WAF or Shield spec is written — running both against the same web ACLs invites conflicting policy ownership.
- **Exam angle:** Domain 3. Too new to be on SCS-C03 yet, but the Firewall Manager comparison is exactly the kind of distinction the exam tests once it lands. The structural difference to remember: Firewall Manager applies a policy to resources; Network Security Manager composes reusable rules into templates into policies and then deploys them with explicit drift state and rollback.
- **Platform angle:** Single-Region (us-east-1) at GA, which matters because our App Plane is multi-region — a global WAF baseline cannot yet be managed from this service for non-us-east-1 ALBs. CloudFront is global so it is covered. Evaluate, do not adopt platform-wide yet.
- **Action:** Add a `network-security-manager` entry to `saas-security/specs-todo.md` and record the Firewall Manager overlap decision in `saas-security/architecture.md`.
- **Source:** [AWS Network Security Manager is now generally available in US East (N. Virginia) Region](https://aws.amazon.com/about-aws/whats-new/2026/09/network-security-manager-us-east-va/)
- **Docs:** [AWS Network Security Manager API Reference — Welcome](https://docs.aws.amazon.com/network-security-manager/latest/APIReference/Welcome.html) · [Standard creation process for AWS Shield Advanced](https://docs.aws.amazon.com/network-security-manager/latest/devguide/managing-shield-standard.html)

### AWS WAF
*Category: Network & Application Protection | Exam domain: 3 - Infrastructure Security | Releases: 1*

#### `P1` 2026-09-22 — CVE-2026-13762 and CVE-2026-13763 — HTTP/2 multi-frame request body inspection
- **What changed:** Two CVEs in how AWS WAF inspects HTTP/2 request bodies. **CVE-2026-13762** affects AWS WAF on CloudFront and was remediated server-side with no customer action. **CVE-2026-13763** affects AWS WAF on Application Load Balancer: a crafted multi-frame HTTP/2 request could cause only a partial request body to be inspected, letting an attacker split a malicious payload across frames to evade a rule. The fix is a target-group attribute, `waf.http2.traffic_inspection_behavior`, shipped 2026-05-22, with two values: `inspect_immediately` (**the default**, inspects whatever request data is available, preserves bidirectional-streaming behaviour) and `inspect_after_sufficient_data` (accumulates HTTP/2 data frames before WAF inspects — AWS's recommended setting for standard request-response applications).
- **Why it matters:** The insecure timing remains the default. Every HTTP/2 ALB target group fronted by a WAF web ACL is exposed until the attribute is explicitly flipped, and nothing in the console warns you. For a multi-tenant API this is a rule-evasion path into the App Plane that bypasses the entire Layer 1 preventive control — the request reaches the application with the malicious portion of the body uninspected. Note AWS states no workaround exists; the attribute change is the remediation.
- **Exam angle:** Domain 3, and a strong candidate for an exam question because it is a *secure-by-configuration, not secure-by-default* case. Know that WAF body inspection on ALB has a timing control, that the default favours streaming compatibility over inspection completeness, and that the trade-off is real: `inspect_after_sufficient_data` can break bidirectional-streaming applications that expect a response before the client finishes sending.
- **Platform angle:** Our documented edge path is CloudFront → API Gateway → NLB → EKS. The CloudFront CVE is already remediated server-side. WAF does not attach to an NLB, so the ALB CVE applies only where an ALB exists — in-cluster ingress via the AWS Load Balancer Controller is the likely place, and those target groups are created by the controller rather than by our CloudFormation, so they need an explicit audit rather than a template change alone.
- **Action:** Audit HTTP/2 ALB target groups and set the attribute; capture `waf.http2.traffic_inspection_behavior=inspect_after_sufficient_data` as a required setting in the forthcoming WAF security configuration catalog.
- **Source:** [AWS Security Bulletin 2026-048-AWS](https://aws.amazon.com/security/security-bulletins/rss/2026-048-aws/)
- **Docs:** [Edit target group attributes — WAF HTTP/2 traffic inspection behavior](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html) · [Considerations for managing body inspection in AWS WAF](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-setting-body-inspection-limit.html)

> **Date note:** this bulletin entered the Security Bulletins feed on 2026-09-22, which is the date the archive windows it on. The bulletin's own stated publication date is 2026-06-29 and the ALB fix shipped 2026-05-22. It is reported here because it first became visible to this collector inside this window, not because it was newly disclosed. Also listed in [Security Advisories](#security-advisories).

### AWS Security Hub
*Category: Detection & Response | Exam domain: 1 - Threat Detection & Incident Response | Releases: 2*

#### `P2` 2026-10-01 — AWS Security Hub introduces remediation plans to prioritize and fix security exposures
- **What changed:** Security Hub now groups exposure findings that share a root cause into a **remediation plan**. Each plan carries its own prioritization (Critical/High/Medium/Low), an impact assessment, and step-by-step instructions rendered as AWS CLI, Terraform, CloudFormation, Python, and CDK. Plans are ordered by risk reduction. Crucially, plans are **readable through the API**, so automation and AI agents can consume them rather than parsing individual findings.
- **Why it matters:** Changes the unit of remediation from a finding to a root cause. One over-permissive IAM policy that produced forty exposure findings becomes one plan. At 1,000 tenants the practical effect is that the responsive-controls layer can act on a root cause instead of forty EventBridge events for the same underlying defect. Available at no additional cost under the Security Hub Essentials plan, so there is no cost argument against adopting it.
- **Exam angle:** Domain 1. Reinforces the exposure-findings model of the newer Security Hub (OCSF-based) against classic Security Hub CSPM control findings. Expect questions on which Security Hub tier/plan surfaces exposures versus standards-based controls.
- **Platform angle:** Target the remediation-plan API from the Audit Account where Security Hub is the delegated administrator. Prefer plan-level automation over per-finding automation in the Layer 3 design.
- **Action:** Design the responsive-controls automation around the remediation-plan API in the Security Hub spec.
- **Source:** [AWS Security Hub introduces remediation plans to prioritize and fix security exposures](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-security-hub-remediation-plans/)

#### `P2` 2026-09-21 — Transforming Bedrock Guardrails events into OCSF with CloudWatch
- **What changed:** A Security Blog walkthrough, but it pins down a mechanism worth recording: the CloudWatch Logs **`ParseToOCSF`** log-transformation processor performs OCSF normalization at ingestion for exactly five AWS log sources — CloudTrail, Route 53 Resolver, VPC Flow Logs, EKS audit logs, and AWS WAF. Bedrock Guardrails is **not** one of them, so guardrail traces embedded in Bedrock model-invocation logs need a custom AWS Lambda transform to become OCSF Detection Finding records before landing in the CloudWatch unified data store (Iceberg-compatible via S3 Tables, queryable from Athena or Logs Insights).
- **Why it matters:** The five-source `ParseToOCSF` list is the boundary between "normalization is free" and "you build a Lambda". Anything outside it that you want correlated with CloudTrail and VPC Flow Logs in one catalog needs a transform step you own and operate. The post also clarifies the division of labour with GuardDuty AI Protection: AI Protection is managed detection over Bedrock CloudTrail data events, while this pipeline preserves the raw guardrail intervention records for your own correlation and long-term trend analysis.
- **Exam angle:** Domain 2 and Domain 7. Know that OCSF normalization in CloudWatch is source-limited, and know the GuardDuty-AI-Protection-versus-custom-pipeline split.
- **Platform angle:** Only applies once the platform uses Bedrock. Worth noting now because four of the five natively supported sources — CloudTrail, VPC Flow Logs, EKS audit logs, WAF — are all sources we already run, so native OCSF normalization is available to us for those without custom code.
- **Action:** Record the `ParseToOCSF` five-source limit in the Security Lake / logging spec.
- **Source:** [Transforming Bedrock Guardrails events into OCSF with CloudWatch](https://aws.amazon.com/blogs/security/transforming-bedrock-guardrails-events-into-ocsf-with-cloudwatch/)
- **Docs:** [ParseToOCSF API reference](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_ParseToOCSF.html)

#### `P2` 2026-09-30 — Uncover blind spots in AWS data plane operations with CloudTrail Event Coverage
- **What changed:** A new console experience that enumerates, per account and across the organization, which AWS services and resource types have **data event** logging enabled and which do not, and lets you subscribe to data events from that dashboard. Previously this required scanning trail configurations account by account.
- **Why it matters:** Management events are on by default; data events are not, and they are the ones that catch `GetObject`-style exfiltration. The unlogged-data-event gap is the single most common blind spot in a multi-account estate, and this turns a manual audit into a dashboard read. For a tenant-data platform, an unlogged S3 prefix is an undetectable exfiltration path, not merely a compliance finding.
- **Exam angle:** Domain 2. The management-versus-data-event distinction, data events being opt-in and separately billed, and which services support data events are all standing exam material. Event Coverage is the new console answer to "how do I find accounts without data event logging".
- **Platform angle:** Run from the Management Account or the Logging Account against the org trail; close gaps on the tenant-data S3 buckets and on any service holding tenant data.
- **Action:** Add an Event Coverage read as a validation checkpoint in the CloudTrail spec's `guide.md`.
- **Source:** [Uncover blind spots in AWS data plane operations with CloudTrail Event Coverage](https://aws.amazon.com/about-aws/whats-new/2026/09/aws-cloudtrail-event-coverage/)
- **Docs:** [Logging data events with CloudTrail](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html#logging-data-events)

#### `P2` 2026-09-18 — Documented redacted AWS CloudTrail event fields for Custom Detection Rules
- **What changed:** Documentation now states explicitly that an AWS service can redact the value of a field in the CloudTrail events it publishes, and that a GuardDuty **Custom Detection Rule** whose detection logic depends on a redacted field **does not match**. This is a documented behaviour, not a new feature.
- **Why it matters:** This is a silent-failure mode, which makes it more dangerous than an error. A custom rule written against a field the publishing service redacts never fires and never reports why — the detection appears configured and healthy while covering nothing. Any custom rule in the detective layer needs to be validated against actual event payloads rather than against the field list in an API reference.
- **Exam angle:** Domain 1 and Domain 2. The exam-testable idea is that detection logic is only as good as the field fidelity of the log source, and that absence of a finding is not evidence of absence of activity.
- **Platform angle:** Audit every GuardDuty Custom Detection Rule we author. Validation for custom rules must assert on a real matching event, not on successful rule creation.
- **Action:** Add a "validate custom rules against a real event payload" step to the GuardDuty spec's `validate.sh`.
- **Source:** [GuardDuty Documentation History — Documented redacted AWS CloudTrail event fields for Custom Detection Rules (2026-09-18)](https://docs.aws.amazon.com/guardduty/latest/ug/#Documented_redacted_AWS_CloudTrail_event_fields_for_Custom_Detection_Rules_2026-09-18)

#### `P2` 2026-10-01 — Announcing DNS analytics and insights for Route 53 Global Resolver and DNS Firewall
- **What changed:** Native CloudWatch integration for Route 53 Global Resolver and DNS Firewall. DNS query logs become searchable through CloudWatch Metrics and Contributor Insights, metric filters can target specific patterns such as blocked queries and DNS response codes, and alarms can fire on those filters. A new **Analytics** tab appears in both consoles. Metrics are opt-in and billed at standard CloudWatch rates. - **Why it matters:** DNS Firewall was previously a control you configured and then read logs from after the fact. It now has an alerting path, which moves it from purely preventive to preventive-plus-detective. Blocked-query volume per VPC is one of the cleanest early indicators of malware beaconing or C2 inside an EKS workload, and per-VPC attribution gives tenant-adjacent blast-radius signal in a pooled architecture.
- **Exam angle:** Domain 2 and Domain 3. DNS Firewall query logging versus the new metrics path, and the fact that the metrics are opt-in and billed, are both plausible question material.
- **Platform angle:** Add a blocked-query alarm per Workload-account VPC to the detective baseline. Opt-in means it is not on by default — this is a deployment task, not an automatic gain.
- **Action:** Add the metric filter and alarm to the Route 53 DNS Firewall spec's `template.yaml`.
- **Source:** [Announcing DNS analytics and insights for Route 53 Global Resolver and DNS Firewall](https://aws.amazon.com/about-aws/whats-new/2026/10/route-53-dns-analytics-insights/)

#### `P2` 2026-09-29 — Route 53 Resolver DNS Firewall support for Palo Alto Networks Advanced DNS Security is GA
- **What changed:** Third-party DNS threat intelligence from Palo Alto Networks is now generally available as DNS Firewall rules across 32 Regions — every Region where DNS Firewall is offered. Rule categories include Command and Control, Malware, Phishing, and Newly Registered Domains. Subscription is through the Route 53 DNS Firewall console; licences are shareable across organization accounts via **AWS License Manager**; and the resulting rule groups are associated with VPCs via **AWS RAM**, **Route 53 Profiles**, or **AWS Firewall Manager**. No separate firewall appliance and no VPC configuration change.
- **Why it matters:** Managed third-party threat intel inside the native DNS control path, with no inline appliance to run or scale. For a multi-region EKS platform this removes the usual trade-off between third-party DNS intel quality and the operational cost of a self-managed DNS proxy fleet. The three distribution mechanisms — RAM, Profiles, Firewall Manager — matter at 1,000-tenant scale because Profiles plus RAM is how one rule group reaches many VPCs without per-VPC configuration.

#### `P2` 2026-09-25 — IAM outbound identity federation now supports interface VPC endpoints for OIDC discovery
- **What changed:** The OIDC discovery metadata endpoint and the JWKS verification-key endpoint used by IAM outbound identity federation are now reachable through an **interface VPC endpoint** (AWS PrivateLink). Pair it with the general point that most AWS API surfaces now have interface-endpoint equivalents.
- **Platform angle:** Add to the VPC endpoint inventory for private subnets if any Control Plane workload uses outbound federation. No change needed if the platform only does inbound federation.
